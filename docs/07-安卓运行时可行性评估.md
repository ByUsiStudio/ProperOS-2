# ProperOS 2.5 Mobile · 安卓软件运行时可行性评估

- 开发者：ByUsi Studio · 北啊呢
- 评估对象：`miao.byusistudio.*` 生态下，能否运行标准 Android APK
- 结论日期：2026-11-25

---

## 1. 结论

**可行，但形态只能是「会话级 Android」，不是「应用级无缝窗口」。**

在现有内核、容器、分区、图形四层中，**内核层与容器层已经具备条件（已实测）**，真正的工程量集中在**图形管线**与**输入/生命周期接管**两处，存储分区需要重新规划。

| 层次 | 现状 | 判断 | 需要做的事 |
| --- | --- | --- | --- |
| 内核 | 7.3.6 arm64，binder 未编入 | **可满足**（已实测编译通过） | 打开 12 个 CONFIG，重编内核 |
| 容器 | podman 4.3 rootful + fuse-overlayfs + slirp4netns | **已满足，零改动** | 无 |
| 图形 | 仅 `/dev/fb0` 直绘 + simpledrm，无 Mesa/EGL/Wayland | **最大缺口** | 引入 DRM 独占会话 + 软件 GLES |
| 输入 | 启动器独占 `/dev/input/event*` | **需新增接管逻辑** | 会话切换时交接 evdev |
| 存储 | `/data` 仅 768 MiB | **不足** | 重划分区至 ≥8 GiB |
| 应用模型 | `.papp` 沙箱（清 cap + uid 10000） | **不适用** | 新增独立的 AndroidSession 服务 |

一句话版本：**内核和容器不用改架构，图形栈要新增一层，应用模型要新增一类实体。**

---

## 2. 已完成的实测验证

不是纸面推演，以下三项在本机实际执行过。

### 2.1 binder 系列配置可启用

对 7.3.6 源码执行 `scripts/config` + `olddefconfig`，全部生效：

```text
CONFIG_ANDROID_BINDER_IPC=y
CONFIG_ANDROID_BINDERFS=y
CONFIG_ANDROID_BINDER_DEVICES="binder,hwbinder,vndbinder"
CONFIG_DMABUF_HEAPS=y
CONFIG_DMABUF_HEAPS_SYSTEM=y
CONFIG_DMABUF_HEAPS_CMA=y
CONFIG_UDMABUF=y
CONFIG_MEMFD_CREATE=y
CONFIG_PSI=y
```

`CONFIG_MEMFD_CREATE` 原本已开启，`PSI` 原本关闭（Android 12+ 的 lmkd 依赖 PSI 做内存压力回收），现已可开。

### 2.2 `drivers/android/` 编译通过

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j5 drivers/android/
# exit 0，耗时 9.7s，built-in.a 生成
```

说明 7.3.6 的 binder 驱动与当前工具链、当前 `MODULES=n` 的纯内建构建方式**完全兼容**，不存在版本断层。

### 2.3 现有图形与 DRM 能力

```text
CONFIG_DRM=y
CONFIG_DRM_VIRTIO_GPU=y
CONFIG_DRM_VIRTIO_GPU_KMS=y
CONFIG_DRM_FBDEV_EMULATION=y
```

virtio-gpu 带 KMS，意味着 **QEMU 环境下存在 `/dev/dri/card0`**，Android 的 SurfaceFlinger 有可用的 DRM 节点。但系统当前只用了 fbdev 模拟出来的 `/dev/fb0`，没有 EGL/GBM/Mesa 用户态。

## 3. 候选方案对比

| 方案 | 原理 | 内核依赖 | 图形依赖 | 适配本系统 | 判断 |
| --- | --- | --- | --- | --- | --- |
| **redroid** | Android 用户空间打成容器，podman 直接跑 | binderfs + memfd/dma-heap | `/dev/dri`（guest 软件渲染） | 高，容器栈已就绪 | **推荐** |
| Waydroid | LXC + 完整 Android 镜像 + Wayland 合成器 | binder | **必须 Wayland + Mesa** | 低，需新增整条 Wayland 栈 | 备选 |
| Anbox | LXC + Android 7，已停更 | binder + ashmem | 需要主机合成器 | 低，镜像过旧 | 排除 |
| libhybris | 直接加载 Android 的 gralloc/HWComposer | 厂商内核驱动 | 厂商 GPU 二进制 | 极低，绑定特定 SoC | 排除 |
| AOSP/Cuttlefish | 完整虚拟设备 | KVM | gfxstream | 极低，资源开销过大 | 排除 |
| APK 转译/兼容层 | 重实现 framework | 无 | 无 | 不存在成熟方案 | 不可行 |

选择 redroid 的核心理由：它把 Android 当作**普通 OCI 容器**运行，与已有的 `podman + fuse-overlayfs + netavark` 完全对齐，不需要引入 LXC、不需要 Wayland、不需要改内核架构；且官方 arm64 镜像与 7.3.6 的 binder 协议代际一致。

镜像实测数据（Docker Hub）：

| 版本 | 压缩体积 | 说明 |
| --- | --- | --- |
| `14.0.0_64only` | 709 MB | 推荐，纯 64 位，展开约 2.2 GB |
| `13.0.0_64only` | 683 MB | 内存更省 |
| `15.0.0_64only` | 730 MB | PSI 依赖更强 |

## 4. 缺口逐项分析

### 4.1 内核：改动量最小的一环

需要新增的配置（约 12 项，已在 10-kernel.sh 的 `scripts/config` 段落追加即可）：

```text
--enable ANDROID_BINDER_IPC --enable ANDROID_BINDERFS
--enable DMABUF_HEAPS --enable DMABUF_HEAPS_SYSTEM --enable DMABUF_HEAPS_CMA
--enable UDMABUF --enable PSI --enable MEMFD_CREATE
```

`CONFIG_ANDROID_BINDER_DEVICES` 设为 `binder,hwbinder,vndbinder`。binderfs 由容器启动时挂载，不占用静态设备号。

代价：内核全量重编约 18 分钟（配置变更触发大部分对象重建），Image 体积从 50 MB 增至约 52 MB。

### 4.2 容器：已经具备，但有三个细节

现有 rootfs 已含 `podman/buildah/skopeo/fuse-overlayfs/slirp4netns/netavark`，rootful 运行，`--privileged` 可用。需要注意：

1. **不能复用 `.papp` 沙箱**。`papp.c` 会 `setuid(10000)` 并 `capset` 清空全部 capability，而 Android 容器需要容器内 root、需要挂载 binderfs、需要操作 netd。二者模型互斥。
2. **binderfs 挂载点**要放在 `/dev/binderfs`，由 AndroidSession 服务在启动容器前 `mount -t binder binder /dev/binderfs`，容器内 `--device /dev/binderfs`。
3. **网络**用独立的 netns（podman 默认），Android 侧 `adb` 走 `127.0.0.1:5555`，不对外暴露。

### 4.3 图形：唯一的真实断层

这是决定「能不能用」而不是「能不能跑」的地方。

现状：启动器直接 `mmap(/dev/fb0)` 逐像素绘制，全系统没有任何 EGL/GLES/GBM/Wayland 用户态组件。

Android 的 SurfaceFlinger 必须有一个显示后端，redroid 提供三种 `redroid_gpu_mode`：

| 模式 | 后端 | 本系统可用性 |
| --- | --- | --- |
| `guest`（默认） | SwiftShader 软件 GLES + minigbm → `/dev/dri` | **可用**，QEMU 与真机都能跑 |
| `host` | 主机 GPU 驱动 + gralloc | 需厂商 GPU 用户态，暂不可用 |
| `auto` | 自动探测 | 会回落到 guest |

因此现实路径是 `guest` 模式：Android 通过 DRM/KMS **独占主平面**输出，软件渲染。

由此产生一个架构约束：**fb0 与 Android 的 DRM master 不能共存**。启动器持有 fb0 时，SurfaceFlinger 拿不到 DRM master。必须做「会话切换」：

```text
启动器会话                           Android 会话
─────────────────────────────────────────────────────────
properos-shell 持有 /dev/fb0    →    systemctl stop properos-shell
fbcon 绑定 vtcon1               →    echo 0 > /sys/class/vtconsole/vtcon1/bind
                                     podman start android
                                     SurfaceFlinger 取 DRM master，独占扫描输出
返回：反向执行，chvt 7 + 重启 properos-shell
```

这条路径的优点是改动可控（一个切换脚本 + 两个 systemd 单元），缺点是**Android 全屏独占**，无法与 Linux 应用同屏。对手机形态而言这恰好是可接受的交互（进入「安卓模式」/ 退出），也符合国产双框架机型的实际做法。

若未来要做「同屏窗口化」，需要引入 Wayland 合成器（weston + wlroots），并把启动器改写成 Wayland 客户端或全屏合成器宿主。那是 3-4 周量级的独立工程，**不建议在第一阶段做**。

### 4.4 输入：需要交接而不是共享

启动器通过 `evdev` 直接读触摸与按键。Android 侧需要自己的输入源。三个层次：

1. PoC 阶段：`adb shell input tap/swipe` 验证画面与逻辑正确，不接真实触摸。
2. 可用阶段：容器内 `--device /dev/input/eventX`，让 Android 的 `EventHub` 直接读 evdev；启动器在进入 Android 前 `EVIOCGRAB` 释放并 `close` 设备。
3. 完善阶段：用 `uinput` 做一层坐标映射与手势仲裁，支持边缘手势返回启动器。

输入不是阻塞项，但**必须与图形切换在同一时刻完成交接**，否则会出现「画面切了但触摸还打在启动器上」。

### 4.5 存储：数字上明确不够

| 分区 | 当前 | Android 需求 | 结论 |
| --- | --- | --- | --- |
| ESP | 256 MiB | 不变 | 够 |
| system | 3 GiB（只读） | 不变 | 够 |
| data | **768 MiB** | 镜像 2.2 GB + 用户数据 4-6 GB | **不足，至少 8 GiB** |

修改点很小：`build/arch/arm64/40-image.sh` 的 `DATA_MIB=768` 改为 `8192`，镜像总大小从 4.1 GB 变为约 11.5 GB。若目标机型存储紧张，可把 Android 镜像放到独立的第三个分区（`/android`），与用户数据隔离，便于整块替换升级。

### 4.6 应用安装：可复用 `.papp` 外壳，但不能复用执行路径

建议新增一种包类型而非新格式：

```text
foo.papp
├── manifest.conf     TYPE=android
│                     PACKAGE=miao.byusistudio.foo
│                     MIN_SDK=29
├── payload/app.apk
└── SHA256SUMS
```

`papp install` 识别 `TYPE=android` 后不建沙箱，而是：解包 APK → `adb install -r` 到运行中的 Android 容器 → 在启动器网格里生成一个 `miao.byusistudio.foo` 图标，点击即 `am start`。

这样包管理体系（ppkg 哈希校验、签名、依赖、卸载）全部复用，只是执行分支不同。改动集中在 `papp.c` 的 install 分支约 150 行。

## 5. 建议的架构落点

新增一个**特权**服务 `properos-android.service`，由 properd 管理，与 `properos-shell.service` 平级：

```ini
[Unit]
Description=ProperOS Android Session
After=network.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/lib/properos/android-session start
ExecStop=/usr/lib/properos/android-session stop
```

`android-session` 脚本职责单一：挂 binderfs → 起容器 → 等 `sys.boot_completed` → 释放 fbcon。退出时反向。

启动器侧只需要一个入口：网格里固定的「Android」磁贴，点击写 `/run/properos/session=android` 并 `systemctl start properos-android`，随后自己 `exit`。

这条设计与现有架构的一致性很高：properd 管服务、启动器管入口、papp 管包，**唯一的例外是 Android 容器不降权**——这一点必须在代码注释里写清楚，避免后来者误把它塞进 papp 沙箱。

## 6. 分期与工作量

| 阶段 | 目标 | 内容 | 预估 |
| --- | --- | --- | --- |
| **P0 可行性** | 证明能开机、能装 APK | 内核加 12 项 CONFIG 重编；`podman run --privileged redroid:14.0.0_64only`；`adb install` 一个测试 APK；`adb shell input tap` 验证画面 | 2-3 天 |
| **P1 可用** | 能从启动器进入并退出 | 分区扩至 8 GiB；`android-session` 脚本；VT/DRM 交接；evdev 交接；启动器磁贴 | 1.5-2 周 |
| **P2 好用** | 日常可用 | uinput 手势映射、APK 包类型接入 ppkg、Android 数据备份/重置、性能调优（fps/dpi） | 2-3 周 |
| P3 同屏窗口化 | Linux 应用与安卓应用混合 | Wayland 合成器 + 启动器改写 | 独立立项，不建议近期 |

总判断：**P0 风险很低，P1 有明确的工程路径，P2 是持续打磨。** 若只做 P0，两天内就能给出「能跑」的结论。

## 7. 性能预期（必须提前对齐预期）

| 环境 | 渲染 | 预期 |
| --- | --- | --- |
| QEMU virt（TCG 模拟） | SwiftShader 软件 | 开机 1-3 分钟，画面 1-3 fps，仅用于功能验证 |
| 真机 A76 级别，720p | SwiftShader 软件 | 开机 25-40 秒，日常应用 15-25 fps，视频类明显掉帧 |
| 真机 + 厂商 GPU（host 模式） | 硬件 GLES | 流畅，但需要 gralloc/HWC 适配，属长期课题 |

**软件渲染在真机上「能用但不快」**，这是必须如实告知用户的一点。想达到原生流畅度，必须走 host 模式，而 host 模式要求把厂商的 GPU 用户态（Mali/Adreno 的 gralloc 与 HWC）桥接到容器里——这本质上是 libhybris 的工作，与具体 SoC 强绑定，不能作为通用交付。

## 8. 明确不推荐的路径

- **不要用 Anbox**：最后版本停在 Android 7，镜像与 7.3.6 的 binder 已不匹配，且项目已归档。
- **不要为 Android 引入 LXC**：podman 已经能满足，多一套容器运行时只会增加攻击面与维护成本。
- **不要把 Android 塞进 `.papp` 沙箱**：能力模型冲突，必然启动失败。
- **不要在第一阶段写 Wayland 合成器**：投入产出比最低，且会把「能否跑起来」的验证推迟数周。

## 10. 最终判断

> 内核不是障碍（已实测），容器不是障碍（已具备）。真正的工作量在图形会话切换与输入交接，属于**可预估、可分期、无技术死路**的工程问题。若目标是「手机上能装能跑常见 APK」，P0+P1 约两周可达成；若目标是「与 Linux 应用同屏无缝」，则需要一次独立的显示架构升级，应单独立项。

风险等级：**中低**。唯一的不可控项是目标真机的 GPU 用户态，只能靠 `guest` 软件渲染兜底。
